\subsection{Dynamic Shape in Deep Learning} 
\label{sec:dynamic-shape}


Deep learning systems were historically optimized under the static-shape assumption, 
where tensor dimensions are fixed before compilation and remain unchanged across executions. 
%This assumption allows compilers and vendor libraries to specialize memory layouts, loop bounds, 
%tiling factors, and kernel launch configurations for a single concrete shape. 
Modern deep learning 
workloads, however, frequently violate this assumption. Dynamic shapes arise from intrinsic data variability, 
such as variable sentence lengths in NLP~\cite{vaswani2017A,devlin2019bert} 
and diverse image resolutions in vision models~\cite{ren2015faster}. 
They also arise from system-level 
execution dynamics, including changing batch sizes, request composition, prompt lengths, generated sequence lengths, 
and KV-cache sizes in LLM serving~\cite{touvron2023llama,dao2022flashattention,jiang2024minference}. Even within 
a fixed model architecture, the same operator type can appear with different dimensions at different layer positions 
or execution phases, which turns a single static operator into a family of dynamic tensor programs~\cite{zheng2022dietcode,zhou2025helix}.

% because the change of arithmetic intensity, memory footprint, data reuse, and available parallelism
The prevalence of dynamic shapes creates practical problems for program execution. 
A kernel schedule tuned for one sequence length or matrix dimension may become inefficient 
for another. Padding and bucketing are common workarounds, but they convert irregular inputs into 
a small set of supported shapes by adding redundant computation and memory traffic; when the actual input is 
much smaller than the padded shape, the wasted work can dominate execution~\cite{fegade2022cora,mu2024ftuner}. 
Compiling or auto-tuning a separate implementation for every possible shape is also impractical, since conventional 
tensor-program search spaces are often shape-dependent and the number of shape combinations grows 
quickly~\cite{chen2018tvm,ragan2013halide,zheng2020ansor,zheng2022dietcode}. Sample-driven dynamic-shape compilers 
reduce this cost by tuning for representative shapes, but their performance can degrade when runtime inputs fall outside 
the sampled set, and changing the sample set usually requires additional tuning~\cite{shen2021nimble,zhou2025helix}.

Dynamic shapes further complicate graph-level optimizations. Operator fusion, memory planning, and template selection 
depend on tensor extents because shape values determine intermediate tensor sizes, reuse distance, and whether temporary data 
can fit in on-chip memory. A fusion decision that is profitable for one runtime shape may increase register pressure, 
exceed shared-memory capacity, or reduce occupancy for another.

\subsection{Tiled Program Compilation}
\label{sec:compilation}
% Triton, TileLang, cuTile ...

Tiled program compilation has become a cornerstone of modern deep learning compiler design by mapping tensor computations onto GPU architectures. The core principle of tiling involves partitioning large-scale 
tensor operations into smaller, cache-friendly sub-blocks (\textit{tiles}) that fit within fast on-chip memory, such as 
shared memory (SMEM) and register files. By iteratively processing these tiles, compilers can maximize data reuse, 
drastically reduce costly global memory transactions, and expose fine-grained parallelism across streaming multiprocessors (SMs). In the tiled compilation paradigm, computational graphs are systematically 
decomposed into tile-level execution units
%, with explicit control over data movement, computation scheduling, and synchronization. 
This abstraction not only mitigates memory bandwidth bottlenecks but also provides a structured optimization 
space for hardware-aware kernel generation, laying the groundwork for domain-specific languages (DSLs) that automate low-level 
GPU programming.

Among the tiled programming works, Triton~\cite{tillet2019triton} has emerged as a paradigm-shifting Python-based DSL and 
compiler infrastructure, offering a high-level interface that abstracts CUDA complexities while serving as the default backend 
for PyTorch 2.x's \texttt{torch.compile} (\texttt{TorchInductor}). By translating framework-level IR into optimized GPU kernels 
through multi-stage transformations and tile-level scheduling, Triton effectively bridges high-level optimizations with 
hardware execution. Nevertheless, its tile scheduling and memory planning often rely on static heuristics or compile-time 
auto-tuning, which can struggle to adapt efficiently to highly dynamic tensor shapes and unpredictable runtime memory access 
patterns.

Recent tiled compilation systems further refine scheduling via hardware-aware abstractions. 
cuTile~\cite{nvidia25cutile} provides a Python-based interface that automatically leverages NVIDIA GPU features (e.g., Tensor Cores (TC) and TMAs) while treating tiles as
first-class immutable values for fine-grained data movement control. TileLang~\cite{cheng2025pipethreader}, built upon 
TVM~\cite{chen2018tvm}, addresses the limitation of ad-hoc, operator-specific pipelining in prior works like Triton and 
CUTLASS~\cite{nvidia22cutlass} by introducing the sTask-graph abstraction, a fine-grained dependency representation that 
decouples tiling from pipeline scheduling, enabling automatic discovery of efficient schedules for both established patterns 
(e.g., FlashAttention) and emerging operators. Nevertheless, these approaches still predominantly assume static or profile-determined 
tensor shapes, leaving dynamic-shape adaptation as an open challenge that motivates our memory-access-guided fusion and 
shape-adaptive auto-tuning.

As shown in Figure~\ref{fig:bg-tile}, tiled compilation exposes a compact but performance-critical configuration space. Tile sizes 
determine the amount of data loaded into shared memory and registers, the reuse opportunity inside a thread block, and the 
number of blocks available to occupy SMs. The number of warps controls intra-block parallelism and scheduling pressure, 
while pipeline stages trade memory-latency hiding against additional resource consumption. Since dynamic shapes change the number of tiles, boundary padding, and reuse distance, the best balance among these parameters can vary across inputs even for the same compilation template.

\subsection{Hierarchical Auto-tuning Techniques}
\label{sec:autotuning}
% 从算子融合到参数调优的分层自动调优技术，可借鉴STOF

% Operator Fusion Opportunities. 
In this paper, we define the hierarchical auto-tuning space as the coupled optimization space across graph-level fusion decisions, operator-level kernel mappings and configuration parameters such as tile sizes, warp counts, and pipeline stages.
Existing DL compilers~\cite{ansel2024pytorch} typically rely on predefined fusion rules that apply only to specific operator combinations. To navigate this complexity, researchers often classify tensor operators into memory-intensive (MI) 
and compute-intensive (CI) categories. Early approaches~\cite{zheng2022astitch,niu2021dnnfusion} treat CI operators as non-fusion boundaries, fusing only MI operators 
to reduce off-chip memory traffic. Subsequent works~\cite{shi2023welder,zheng2023chimera} merge CI operators with adjacent MI ones or decompose CI chains into 
fine-grained blocks to balance hardware resource utilization. However, category-based schemes provide limited visibility into whether certain operators 
can be fused and whether such fusion can yield real performance benefits. In addition, the category alone does not reveal how intermediate values are accessed, reused, or materialized in memory, resulting in fused operators whose memory behavior is poorly matched to the target compilation template.

% Search Space Construction
The optimization space for tensor programs is typically constructed via loop-based~\cite{zheng2020ansor,li2023exploiting} or 
template-based~\cite{chen2024evt} paradigms. Loop-based approaches represent operators as deeply nested loops and explore performance through loop 
transformations (e.g., tiling, unrolling, vectorization). While hardware-portable, they often lag behind vendor-optimized libraries due to limited exposure to hardware-specific instructions (e.g., WMMA, TMA, or warp-level primitives). Conversely, template-based methods leverage vendor-provided building blocks
(e.g., CUTLASS~\cite{nvidia22cutlass} or Triton~\cite{tillet2019triton} primitives) to directly map computations to specialized execution units. This 
hardware-knowledge-driven tuning enables peak performance but introduces significant engineering overhead; extending template coverage to novel fusion patterns 
or emerging operators remains highly demanding. Moreover, both paradigms struggle to accommodate shape variability: loop schedules require exhaustive re-derivation 
for new dimensions, while template parameters are typically hard-coded or profiled offline, leaving a critical gap in efficiently scaling search spaces to dynamic 
tensor programs.

% Auto-tuning Techniques.
To navigate the exponentially large search space, existing auto-tuning frameworks employ rule-based pruning, machine learning-driven cost 
models~\cite{zheng2021tenset}, or analytical heuristics~\cite{ragan2013halide}. 
Learning-based predictors train on extensive runtime profiling data to 
estimate performance, guiding evolutionary searches (e.g., genetic algorithms or Bayesian optimization) toward high-performing configurations. 
However, they incur substantial online profiling overhead and lack generalization to unseen shapes or novel fusion boundaries. Analytical models reduce profiling costs by incorporating 
hardware constraints and program semantics but typically assume fixed operator graphs and static tiling strategies. Aggressive decoupling 
techniques~\cite{ansel2024pytorch} unfold computation graphs sequentially to reduce search complexity, yet optimizing each operator in isolation without global 
context frequently leads to suboptimal end-to-end performance. Crucially, prior works fail to provide a unified mechanism to jointly reason about fusion strategies, 
template selection, and tuning parameters under runtime shape variability.
