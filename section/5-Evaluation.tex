\subsubsection{Hardware and Software Platforms} 

We evaluate MAGSAT on two GPU platforms: NVIDIA A100 (Ampere architecture) and H100 (Hopper architecture). 
%These two platforms represent recent NVIDIA GPU generations with distinct differences in hardware resources, 
%enabling us to assess whether the proposed framework remains effective across hardware generations. 
All experiments are conducted on machines running Ubuntu 22.04, with CUDA 12.6 and PyTorch 2.9.0.

\subsubsection{Comparison Configurations and Methods}

We evaluate both operator-level and end-to-end workloads. At the
operator level, we use representative GEMM and convolution workloads,
which cover the compute-intensive primitives commonly appearing in
Transformer and CNN models. For the end-to-end workload, we evaluate four
representative models: BERT~\cite{devlin2019bert},
LLaMA~\cite{touvron2023llama}, ResNet~\cite{he2016resnet}, and
AlexNet~\cite{krizhevsky2012alexnet}. These models exercise both
GEMM-dominated and convolution-dominated computation patterns.

We compare MAGSAT with five baselines. Torch Native denotes eager-mode
PyTorch execution. Torch Compile~\cite{ansel2024pytorch} denotes the PyTorch
2.x compiler stack based on TorchDynamo and
TorchInductor. CUTLASS is NVIDIA's
template-based GPU kernel library~\cite{nvidia22cutlass}. DietCode~\cite{zheng2022dietcode} and
Helix~\cite{zhou2025helix} are state-of-the-art systems in
dynamic-shape tensor program compilation. All experiments adopt FP16
inputs and outputs. For timing, we perform 100 warm-up iterations before
measurement and report the average performance.

\subsection{Ablation Study}
\label{sec:ablation}

We use ablation experiments to quantify each MAGSAT component. The
experiments cover both LLM and CNN workloads.
We compare three variants: \textit{Full} enables both operator fusion and
shape-adaptive configuration selection, \textit{Fusion only} keeps
fusion but uses one fixed tile configuration for all shapes, and \textit{Tuning only} disables fusion while retaining the analytical cost model for per-shape tuning. For LLMs, we vary sequence length from 1 to 253
with batch size 1. For CNNs, we vary batch size from 1 to 64.
%All variants are evaluated against Torch Native. 
Figure~\ref{fig:ablation} shows the speedup of each configuration
over Torch Native.

\subsection{Parameter Tuning Efficiency}
\label{sec:tuning}

% 选到的配置相比全局最优配置的性能差别，以及在各种形状下取到最优配置的比例
To evaluate the efficiency of our tuning mechanism, we measure the performance gap between the configurations selected 
by MAGSAT and the per-shape global optimums obtained through exhaustive search. We focus on \texttt{GEMM}-based variants as representative cases, given their dominance as the most critical and time-consuming components in modern 
Transformer-based workloads. Across a diverse set of 85 dynamic shapes, MAGSAT identifies configurations
with a mean performance gap of 11.72\% for \texttt{GEMM\_bias\_layernorm} 
and 12.08\% for \texttt{GEMM\_bias\_act} relative to the theoretical oracle. 
%More notably, when applied to complex fused kernels, this gap narrows significantly to 11.72\% for \texttt{GEMM\_bias\_layernorm} 
%and 12.08\% for \texttt{GEMM\_bias\_act}. 
%This reduction occurs due to the shifted performance bottleneck and the constrained 
%valid search space in fused epilogues. 
Fusing operations like \texttt{layernorm} introduces thread-block reductions 
that inherently increase register pressure and shared memory consumption. This architectural constraint heavily prunes the valid search 
space by eliminating overly large tile sizes that would otherwise cause register spilling.
%, effectively flattening the performance landscape 
%and allowing the tuner to converge near the global optimum more easily. 
Ultimately, by accepting a marginal performance 
loss compared to the oracle, MAGSAT successfully bypasses the prohibitively expensive exhaustive search process, delivering a highly 
practical strategy for dynamic shapes.

\subsection{Overhead Analysis}
\label{sec:overhead}

We divide the overhead of our system into offline and runtime components.
Offline overhead includes graph-level fusibility analysis, which takes 244.0 ms
on median for matmul-bias-ReLU. This analysis occurs only once with a fixed the network structure, independent of dynamic input.
Also, the compilation cost is only incurred for unseen shapes and can be effectively amortized via cache reuse.
For runtime overhead, 
we compare against exhaustive autotuning, which
evaluates all candidate configurations for each shape and takes 363.5 s per
shape on median across 170 cases. In contrast, our approach directly invokes compiled fused kernels and performs online configuration selection with sub-millisecond overhead.
